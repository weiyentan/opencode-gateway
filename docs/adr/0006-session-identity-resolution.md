# ADR 0006: Session identity resolution — external IDs mapped to internal UUIDs at ingest time

## Status

Accepted

## Context

The Gateway collects telemetry from OpenCode serve instances. Each
usage record originates from an OpenCode SQLite database, where
sessions are identified by native `ses_*` strings (e.g., `ses_abc123`).
These external session IDs are not UUIDs — they are opaque strings
generated by the OpenCode client.

The Gateway schema already anticipated this split during initial
design: the `sessions` table has both a UUID primary key (`id`) and an
`external_session_id` column. The ingest API receives `session_id` as
a free-form string on the wire and must decide whether it refers to an
already-known session or a new one.

Two approaches were considered for the resolution mechanism:

1. **Separate mapping table** — a `session_mappings` table that maps
   `(source_database_id, external_session_id)` to `sessions.id`,
   keeping the resolution logic separate from the session row itself.
2. **Inline resolution via upsert** — resolve directly on the
   `sessions` table using a unique index on
   `(source_database_id, external_session_id)` with a SQL upsert
   (INSERT … ON CONFLICT …).

## Decision

Use inline resolution (option 2). At ingest time, `_resolve_session()`
maps `(source_database_id, external_session_id)` to an internal
`sessions.id` UUID via upsert. No separate mapping table is needed.

A unique index on `(source_database_id, external_session_id)` WHERE
`external_session_id IS NOT NULL` enforces the invariant that each
external session ID maps to exactly one internal UUID per source
database.

## Rationale

- **Schema simplicity**: one table instead of two — the `sessions`
  table already carries the `external_session_id` column, so the
  mapping is stored in place.
- **Stable identity**: internal UUIDs are stable per external ID per
  source database. The same OpenCode session always resolves to the
  same gateway session UUID, even across restarts or re-ingests.
- **No sync problem**: because the mapping lives on the session row
  itself, there is no separate mapping table to get out of sync.
- **Partial index avoids null noise**: usage records without an
  external session ID (e.g., anonymous telemetry) are not forced into
  the uniqueness constraint. The partial index only covers rows where
  `external_session_id IS NOT NULL`.

## Consequences

Positive:
- Simpler schema — no extra mapping table or join
- Resolution is a single upsert, not a two-step lookup-then-insert
- Internal UUIDs are deterministic per (source DB, external ID) pair
- The partial index allows nullable external session IDs without
  constraint violations

Negative:
- The session row itself must be updated on first reference (upsert
  writes to `first_message_at` / `last_message_at` on every ingest,
  which is already required for aggregate counting)
- Cannot support multiple internal sessions mapping to the same
  external ID (this is intentional — it would break the identity
  invariant)
- `_resolve_session()` must use a transaction-safe upsert pattern;
  a naive read-then-write risks race conditions under concurrent
  ingestion

## Schema Detail

```sql
-- Unique index (to be applied via migration)
CREATE UNIQUE INDEX ix_sessions_external_id_per_source
    ON sessions (source_database_id, external_session_id)
    WHERE external_session_id IS NOT NULL;
```

The `_resolve_session()` function (to be implemented in the ingest
handler) performs:

```sql
INSERT INTO sessions (id, client_id, source_database_id, external_session_id,
                      first_message_at, last_message_at)
VALUES (gen_random_uuid(), :client_id, :source_database_id, :external_session_id,
        :reported_at, :reported_at)
ON CONFLICT (source_database_id, external_session_id)
    WHERE external_session_id IS NOT NULL
DO UPDATE SET last_message_at = GREATEST(sessions.last_message_at, :reported_at)
RETURNING id;
```

This pattern is idempotent and safe for concurrent callers.

## Alternatives Considered

**Separate mapping table**: A `session_mappings` table with
`(source_database_id, external_session_id, internal_session_id)` would
decouple the mapping from the session aggregate data. This was
rejected because it adds a join to every session lookup without a
compelling benefit — the mapping is always 1:1 and the `sessions`
table already carries both IDs.

**Client-provided UUIDs**: The gateway could require collectors to
supply a UUID on the wire. This would shift the identity problem
upstream and force OpenCode (or the collector) to maintain a mapping,
duplicating the resolution logic outside the gateway's control domain.
